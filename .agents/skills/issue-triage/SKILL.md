# 이슈 트리아지 — focus / instant / tuck

출처: 이슈 #6(마일스톤 제안), #7(라벨 의미). `f`/`i`/`t`는 약칭일 뿐이며 **새 라벨을 만들지 않는다**.

## 스크립트 (우선 실행)
반복·결정적 작업은 스크립트로 수행하고 요약 출력만 읽는다.
- `scripts/new-issue.sh <focus|instant|tuck> "<title>" [body-file]` — 라벨을 검증(약칭 금지)하고 이슈를 생성한다. body-file 생략 시 stdin. gh CLI 인증 필요.

## 라벨 정의

### `focus` (f) — 집중해서 해야 하는 핵심적인 일
- 사용자 목표에 직접 기여하고 충분한 집중 시간·사고·작업 단위가 필요한 핵심 과제.
- 예: Cloudflare 앱 골격 구축, Kakao OIDC 구현, PASETO 인증 구현, 프로덕션 BDD QA.
- 오래 걸린다는 이유가 아니라 **핵심성 + 집중 필요성**으로 분류한다.

### `instant` (i) — 부수적으로 필요하지만 바로 처리하거나 단위가 적은 일
- 본 작업을 뒷받침하는 운영/정리/간단한 설정, 빠르게 처리 가능한 작은 부수 작업.
- 예: Milestone 생성 요청, GitHub 설정 확인, 작은 문서 수정, 값 등록 확인.
- 단순히 긴급하다는 이유로 분류하지 않는다. 핵심 과제가 급하면 여전히 `focus`가 적절하다.

### `tuck` (t) — 나중에 해도 되거나 미리 정리해 둔 일
- 현재 목표를 막지 않고 보류 가능한 아이디어·개선안·추후 검토 과제.
- 예: 로그인 기능 완료 이후의 사용성 아이디어, 비핵심 테마 고도화 제안.
- 잊지 않도록 기록만 하고, 현재 작업을 대체하여 바로 실행하지 않는다.

## 의사결정 순서
1. 현재의 핵심 목표이며 집중이 필요한가? → `focus`
2. 아니라면 지금 바로 처리해야 하거나 작은 부수 작업인가? → `instant`
3. 아니라면 나중에 해도 되거나 미리 적어두는 일인가? → `tuck`

`focus > instant > tuck` 같은 숫자식 우선순위 대용으로 사용하지 않는다. 작업의 성격, 집중도, 처리 시점을 함께 표현한다.

## 운영 규칙
- 각 이슈는 일반적으로 세 라벨 중 **한 개**만 지정한다(중복 분류 자제).
- 분류가 바뀌면 라벨을 변경하고 사유를 댓글/PR에 남긴다.
- `0.1.0`–`0.5.0` 실제 구현은 `focus`, GitHub Milestone 작성·수정 제안은 `instant`, 추후 개선 아이디어는 `tuck`.
- 기존 GitHub 라벨 `focus`, `instant`, `tuck`을 그대로 재사용한다. **라벨 생성·이름 변경·삭제 금지.**

## Milestone 정책 (이슈 #6)
- Milestone 생성은 **사용자의 수동 작업**이다. 에이전트는 사용자가 명시적으로 요청하지 않는 한 생성·연결하지 않는다.
- 제안된 마일스톤: 제목 `0.x — Kakao Login & Identity`, Due `2026-10-22`(KST, 설명에 19:00 명시), 대상 #1–#5.
- 완료 정의: #1–#5 closed + TDD/BDD/반응형 통과 + 실제 Kakao 계정 smoke 성공 + 배포 URL·커밋 SHA 확인 + PASETO 만료/변조/폐기 검증.
- 마일스톤이 아직 생성되지 않은 상태에서는 이슈 본문의 버전(0.1.0…)과 선행 링크가 우선순위 근거다.
- 다음 기능 단위(1.x) 마일스톤은 요구사항 확정 전까지 만들지 않는다.

## 이슈/PR 관례
- 새 구현 이슈는 선행 이슈를 명시하고 제목에 버전(`0.x.0`)을 포함한다.
- PR에는 테스트 위치/명령/결과, 배포 URL, commit SHA, 남은 blocker를 기록한다.
- 브랜치/PR 플로우: `main ← dev ← 기능 브랜치(feat/fix/chore/docs/test)` — 모든 병합은 PR로만 한다. 직접 push·force push 금지. 상세는 `AGENTS.md`의 브랜치·PR 플로우 참조.
